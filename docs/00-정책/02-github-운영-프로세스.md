## 브랜치 정책

PDForge의 기본 개발 흐름은 다음과 같습니다.

```text
작업 브랜치 → dev → stg → main
```

현재 정책은 다음과 같습니다.

- PR 대상 브랜치는 `dev`만 사용합니다.
- `stg`, `main`에는 직접 PR을 만들지 않습니다.
- `stg`, `main` 승격 정책은 제품 개발 준비가 끝난 뒤 별도 문서로 확정합니다.

## Issue 작성 원칙

Issue는 AI 에이전트에게 일을 맡기기 위한 작업 지시서입니다. 따라서 “무엇을 만들 것인가”뿐 아니라 “어떤 문서를 기준으로 판단할 것인가”를 함께 적어야 합니다.

### Issue 제목 형식

```text
[문서] AI 주도 개발 준비 과정 정리
[기획] PDF 뷰어 핵심 사용자 흐름 정의
[설계] 에이전트 협업 구조 초안 작성
[구현] 문서 업로드 화면 초안 구현
[회고] 준비 단계 회고 작성
```

### Issue 본문에 포함할 내용

- 배경
- 목표
- 참고 문서
- 완료 조건
- 제외 범위
- 회고 문서 작성 여부
- PR에 연결할 Issue 번호 또는 임시 Issue 요약

## PR 작성 원칙

PR은 사람이 최종 검토하기 위한 변경 묶음입니다. AI 에이전트가 PR을 만들더라도 사람은 다음 내용을 확인해야 합니다. PR 본문 첫 줄에는 작업브랜치명을 적습니다.

- 요청한 범위만 변경했는가
- 문서와 코드가 서로 모순되지 않는가
- 테스트/린터 실행 원칙을 지켰는가
- 새로 결정된 내용이 회고에 남았는가

### PR 제목 형식

```text
문서: AI 주도 개발 준비 문서 추가
기획: PDF 뷰어 서비스 요건 초안 정리
설계: 에이전트 협업 구조 문서화
구현: 문서 업로드 화면 추가
```

### PR 본문 템플릿

```md
작업브랜치명: `20260530_Codex_이슈제목현행화`

## 관련 Issue

- Closes #이슈번호
- 관련 Issue가 아직 없으면: 아직 GitHub Issue 미생성

## 작업 내용

- 변경한 내용을 한글로 요약합니다.

## 확인 방법

- 문서 변경만 있는 경우: 문서 검토만 수행했다고 적습니다.
- 코드 변경이 있는 경우: 실행한 테스트/린터 명령을 적습니다.

## 관련 문서

- 관련된 docs 문서 링크를 적습니다.

## 회고

- 작성한 회고 문서 링크를 적습니다.

## 다음 작업

- 이어서 해야 할 작업을 적습니다.
```

## Issue와 PR 연결 규칙

- PR 본문 맨 위에는 `관련 Issue`를 적습니다.
- 실제 GitHub Issue가 있으면 `Closes #번호` 형식으로 연결합니다.
- 아직 Issue가 없다면 `아직 GitHub Issue 미생성`이라고 적고, PR 본문 또는 별도 문서에 Issue 제목, 배경, 목표, 완료 조건, 제외 범위를 요약합니다.
- 자세한 작성 예시는 [`03-issue-pr-작성-가이드.md`](03-issue-pr-작성-가이드.md)를 따릅니다.

## “문서를 원격 저장소에 올리면 에이전트가 알아서 작업하나?”에 대한 답

아닙니다. 문서를 올리는 것만으로 에이전트가 자동으로 일을 시작하지는 않습니다.

보통 다음 순서가 필요합니다.

1. 문서를 원격 저장소에 push합니다.
2. GitHub Issue를 만듭니다.
3. Issue에 목표, 참고 문서, 완료 조건을 적습니다.
4. Copilot coding agent 또는 Codex 같은 에이전트에게 Issue를 할당하거나 프롬프트로 작업을 요청합니다.
5. 에이전트가 브랜치를 만들고 변경을 제안하거나 PR을 만듭니다.
6. 사람이 PR을 검토하고 수정 요청 또는 병합을 결정합니다.
7. 작업 결과와 시행착오를 회고 문서에 남깁니다.
8. PR 본문에는 연결된 Issue 번호 또는 아직 Issue가 없다면 임시 Issue 요약을 남깁니다.

즉, 문서는 에이전트의 “기억”이 아니라 “작업 기준서”입니다. 실제 작업 시작은 Issue 할당, 에이전트 호출, PR 요청 같은 명시적인 트리거가 필요합니다.
