## 목적

이 문서는 PDForge를 pdfrend와 별도의 독립 제품으로 만들기 위해, pdfrend `dev` 브랜치의 `docs` 문서를 서비스 관점에서 분석한 결과를 정리합니다.

분석 기준은 다음과 같습니다.

- pdfrend의 내부 구현 방식은 그대로 복제하지 않습니다.
- 사용자가 얻는 가치와 사용 흐름만 PDForge 후보 요건으로 가져옵니다.
- PDForge의 첫 제품은 “업로드 기반 PDF 작업 뷰어”를 목표로 하며, OCR·목록·주석·서버 저장은 MVP 후보로 두되 클라우드 협업 플랫폼 전체를 한 번에 구현하지 않습니다.

## pdfrend 문서 구조에서 배울 점

pdfrend는 문서를 정책, 기획, 설계, 기술, 테스트, 의사결정, 일정, 이슈, 심화학습, 리뷰관리처럼 주제별로 나눕니다. PDForge도 이 방식을 그대로 참고하되, 제품 초기 단계에서는 다음처럼 단순화합니다.

| pdfrend 구조 | PDForge 현재 구조 | 적용 방식 |
| --- | --- | --- |
| 정책관리 | `00-정책` | 브랜치, PR, 문서, 서비스 정책을 먼저 관리 |
| 기획관리 | `02-기획` | 서비스 요건, 사용자 흐름, 범위 관리 |
| 설계관리 | `03-설계` | 에이전트 협업 구조와 이후 제품 아키텍처 관리 |
| 기술관리 | 추후 `06-기술` 후보 | 실제 스택 결정 후 분리 예정 |
| 테스트관리 | 추후 `07-검증` 후보 | 코드가 생긴 뒤 테스트 전략 분리 예정 |
| 의사결정관리 | 추후 `08-의사결정` 후보 | ADR 문서가 늘어나면 분리 예정 |
| 이슈관리 | `.github/ISSUE_TEMPLATE` + docs | GitHub 템플릿과 문서 체크리스트 병행 |
| 리뷰관리 | `05-회고` | 작업별 회고와 리뷰 기록을 우선 남김 |
| 일정관리 | `06-일정` | 작업 ID 기반 MVP 작업 순서 관리 |
| 이슈관리 | `07-이슈` | GitHub Issue 작성 내용과 번호 추적 |
| PR관리 | `08-PR` | GitHub PR 작성 내용과 번호 추적 |

## 서비스 관점 핵심 가치

pdfrend 문서에서 확인한 핵심 가치는 다음입니다.

1. 사용자는 PDF를 여러 기기에서 이어서 작업하고 싶다.
2. 사용자는 스캔 PDF를 검색 가능한 문서로 바꾸고 싶다.
3. 사용자는 목차, 주석, 북마크를 문서와 함께 체계적으로 관리하고 싶다.
4. 사용자는 주석 작업 중 버전 혼선과 충돌을 줄이고 싶다.
5. 사용자는 공유 문서에서 권한에 맞게 협업하고 싶다.
6. 사용자는 작업 결과를 외부 PDF 도구에서도 열 수 있는 표준 PDF로 다시 받고 싶다.

PDForge는 이 가치를 참고하지만 첫 버전에서는 “사용자가 브라우저에서 PDF를 업로드하고, 읽고, OCR·목록·주석 작업 맥락을 서버에 남기는 경험”에 집중합니다.

## 기능 후보 분류

| 후보 기능 | pdfrend에서의 의미 | PDForge 반영 판단 | 이유 |
| --- | --- | --- | --- |
| PDF 업로드/열기 | 문서 작업의 시작점 | MVP 유지 | 뷰어 제품의 필수 기능 |
| 문서 목록/대시보드 | 내 문서와 공유 문서 관리 | MVP 축소 유지 | 업로드한 문서와 서버 저장 상태를 확인하는 목록으로 단순화 가능 |
| PDF 작업 뷰어 | 읽기, 이동, 주석 작업의 중심 | MVP 유지 | 핵심 제품 경험 |
| 목차 사이드바 | 문서 구조 탐색 | MVP 유지 후보 | 긴 PDF를 읽는 데 중요하지만 자동 목차 생성은 보류 가능 |
| 주석 목록 | 작업 흔적 탐색 | MVP 유지 후보 | 협업이 없어도 개인 작업 관리에 유용 |
| 북마크 | 읽던 위치와 관심 지점 저장 | MVP 유지 후보 | 구현 난이도 대비 사용자 가치가 높음 |
| 문서 내 검색 | OCR/텍스트 기반 탐색 | 단계적 반영 | 텍스트 PDF는 우선, OCR은 이후 단계로 분리 |
| OCR 처리 | 스캔 PDF 검색 가능화 | MVP 후보 | 페이지별 OCR 작업은 필요하지만 실제 엔진 범위는 조정 가능 |
| 실시간 서버 반영 | 브라우저 작업 결과 저장 | MVP 기반 | 작성 내용이 서버에 반영되어야 작업 연속성을 제공할 수 있음 |
| 버전/브랜치/머지 | 주석 충돌과 이력 관리 | 보류 | 협업 단계에서 필요 |
| 오프라인 변경 머지 | 네트워크 단절 후 충돌 처리 | 보류 | IndexedDB 저장 정도로 축소 가능 |
| 공유 권한 | 협업과 접근 제어 | 후보 | 조회 권한과 작업 권한 분리 정책이 필요 |
| 표준 PDF 다운로드 | 작업 결과 외부 도구 호환 | 2차 후보 | 주석 기능 구현 후 필요 |
| 멀티 문서 탭 | 여러 문서 동시 작업 | 2차 후보 | MVP에서는 단일 문서 경험을 먼저 안정화 |
| 페이지 관리 | 페이지 삽입/삭제/순서 변경 | 보류 | 단순 뷰어 범위를 넘어 편집기로 확장됨 |

## PDForge MVP에 남길 서비스 요건 초안

| ID | 요건 | 사용자 가치 | 우선순위 | 상태 |
| --- | --- | --- | --- | --- |
| REQ-001 | 사용자는 브라우저에서 PDF 파일을 업로드하고 열 수 있다 | 설치 없이 업무/스캔 문서 작업을 시작할 수 있다 | 높음 | 후보 확정 |
| REQ-002 | 사용자는 페이지를 이동하고 확대/축소할 수 있다 | 긴 문서를 원하는 방식으로 읽을 수 있다 | 높음 | 후보 확정 |
| REQ-003 | 사용자는 페이지별 OCR 작업을 할 수 있다 | 스캔 문서를 검색·정리 가능한 자료로 바꿀 수 있다 | 높음 | 범위 조정 필요 |
| REQ-004 | 사용자는 목록 작업으로 문서 구조를 정리할 수 있다 | 도서와 긴 문서를 빠르게 탐색할 수 있다 | 중간 | 후보 |
| REQ-005 | 사용자는 주석 또는 메모를 남길 수 있다 | 문서 위에 작업 맥락을 보존할 수 있다 | 높음 | 후보 |
| REQ-006 | 사용자의 작업 결과는 서버에 반영된다 | 다른 세션에서도 작업을 이어갈 수 있다 | 높음 | 서버 구조 필요 |
| REQ-007 | 공유 권한이 있는 문서는 로그인 없이 조회할 수 있다 | 외부 사용자도 허용된 문서를 볼 수 있다 | 중간 | 권한 정책 필요 |
| REQ-008 | OCR/목록/주석 작업은 로그인 상태에서만 가능하다 | 작업 권한을 통제할 수 있다 | 높음 | 인증 정책 필요 |

## MVP에서 제외할 것

다음 기능은 pdfrend에서 중요하지만 PDForge 첫 버전에서는 제외합니다.

- 복수 인증수단과 복잡한 계정 관리
- 사용자별 세밀한 요금/업로드 용량 정책
- 실시간 다중 사용자 공동 편집과 충돌 해결
- Git 방식 브랜치/머지 버전 관리
- 문서 자체 암호화
- 모바일 앱 수준의 최적화
- 페이지 삽입/삭제/재정렬 같은 PDF 편집기 기능
- Xodo 등 외부 도구 완전 호환 PDF 병합 엔진

## 정책으로 가져올 것

pdfrend의 구체 정책을 그대로 적용하지 않고, 운영 방식만 PDForge 정책으로 가져옵니다.

| 정책 영역 | PDForge 적용 방향 |
| --- | --- |
| Issue 후 작업 시작 | 모든 에이전트 작업은 Issue 또는 명시적 작업 요청으로 시작 |
| PR 대상 `dev` | PR 대상 브랜치는 `dev`로 고정 |
| 문서 먼저 갱신 | 정책/요건/설계 변경은 코드보다 문서에 먼저 남김 |
| 작업 후 회고 | 작업 결과와 시행착오를 `docs/05-회고`에 기록 |
| 테스트 계획 | 코드 작업 전 완료 조건과 검증 방법을 Issue에 작성 |
| 참조 문서 링크 | 근거 문서는 해당 위치로 이동 가능한 링크를 남김 |
| 민감 정보 관리 | API 키, 비밀번호 등은 문서와 코드에 직접 기록 금지 |
